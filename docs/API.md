# API Documentation

## Base URLs

| Environment | Base URL |
| --- | --- |
| Local | `http://localhost:8000/api/v1` |
| Production | `https://YOUR-BACKEND-ORIGIN/api/v1` |

The React app reads the backend origin from `VITE_API_BASE_URL`.

---

## Authentication

Most endpoints require a bearer token:

```text
Authorization: Bearer <access_token>
```

Public endpoints:

- `POST /auth/register`
- `POST /auth/login`
- `GET /health`
- root `/`

Register/login return:

```json
{
  "access_token": "...",
  "token_type": "bearer",
  "expires_in": 3600,
  "user": {
    "id": 1,
    "name": "Asha",
    "email": "asha@example.com",
    "created_at": "2026-01-01T00:00:00Z"
  }
}
```

The frontend stores the token locally and clears it on `401`.

## Interactive docs

In development only:

- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`
- OpenAPI JSON: `http://localhost:8000/api/v1/openapi.json`

Interactive docs are intentionally disabled when `ENVIRONMENT=production` or `staging`. Use this document and the typed FastAPI schemas as the stable API reference.

## Endpoints

### Health and app

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/` | No | App name, version, docs flag, health path |
| `GET` | `/api/v1/health` | No | API health ping |
| `GET` | `/api/v1/health/db` | No | PostgreSQL readiness (no raw error detail) |

### Auth and profile

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/register` | No | Create account and return token |
| `POST` | `/api/v1/auth/login` | No | Authenticate and return token |
| `GET` | `/api/v1/auth/me` | Yes | Current user |
| `POST` | `/api/v1/auth/logout` | Optional | Stateless logout acknowledgment |
| `GET` | `/api/v1/profile/me` | Yes | Get student profile |
| `PUT` | `/api/v1/profile/me` | Yes | Create/update student profile |

Register body:

```json
{
  "name": "Asha Verma",
  "email": "asha@example.com",
  "password": "StrongPass123"
}
```

Password rules: 8–72 bytes, at least one letter and one digit.

Login body:

```json
{
  "email": "asha@example.com",
  "password": "StrongPass123"
}
```

Profile body accepts any combination of:

```json
{
  "college": "Example University",
  "degree": "B.Tech",
  "branch": "Computer Science",
  "graduation_year": 2027,
  "target_role": "Backend Engineer"
}
```

### Resumes

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/v1/resumes/upload` | Yes | Upload and parse a PDF resume |
| `GET` | `/api/v1/resumes` | Yes | List current user's resumes |
| `GET` | `/api/v1/resumes/{resume_id}` | Yes | Get parsed resume detail |

Upload uses `multipart/form-data` with field name `file`.

Validation:

- `.pdf` extension
- `%PDF-` magic bytes
- maximum 5 MB
- text-based PDF required
- maximum 50 pages and 2,000,000 extracted characters server-side

### Job descriptions

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/v1/jobs/analyze` | Yes | Analyze a job description |
| `GET` | `/api/v1/jobs` | Yes | List analyzed jobs |
| `GET` | `/api/v1/jobs/{job_id}` | Yes | Get saved job detail |

### Matching

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/v1/analysis/match` | Yes | Create deterministic resume-to-job match |
| `GET` | `/api/v1/analysis` | Yes | List saved matches |
| `GET` | `/api/v1/analysis/{analysis_id}` | Yes | Get saved match detail |

Match body:

```json
{
  "resume_id": 1,
  "job_id": 3
}
```

The 0–100 score is deterministic and never generated by an LLM.

## Response and error format

Successful responses use JSON matching the documented response model. Errors use FastAPI's standard shape:

```json
{
  "detail": "Message"
}
```

Common status codes:

| Code | Meaning |
| --- | --- |
| `400` | Validation/business rule failure |
| `401` | Missing, invalid, expired, or tampered token |
| `404` | Resource not found or not owned by user |
| `409` | Duplicate email |
| `422` | Pydantic request validation failure |
| `502` | AI service failure; detail is intentionally generic |

AI failures never expose upstream messages or API keys.

## AI behavior

If `LLM_API_KEY` is set, AI is used for JD analysis, roadmap recommendations, interview questions, and answer evaluations. All AI output must validate against strict Pydantic contracts before storage.

If no key is set, deterministic local fallbacks are used. Match scores, readiness scores, target-skill counts, and dashboard metrics never depend on AI.
